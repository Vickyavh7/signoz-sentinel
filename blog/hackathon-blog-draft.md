# We Built an SRE Copilot on SigNoz MCP — Then Put the Copilot Under Observability Too

When an alert fires at 2am, the expensive part isn't the paging — it's the scavenger hunt.

Which service?

Which trace?

Which log line?

Which deploy?

For the **Agents of SigNoz** hackathon (Track 01 — AI & Agent Observability), we built **Incident Sentinel**: an SRE copilot that investigates SigNoz alerts using the SigNoz MCP server, posts a root-cause report to Slack, and — the part we actually care about — **observes itself** with OpenTelemetry GenAI semantic conventions in the same SigNoz instance.

The agent that debugs your system should not be a black box.

## The problem

AI agents are showing up in on-call workflows. They call tools, reason over telemetry, and write summaries. But when the agent is wrong — or slow, or expensive — teams often have no span, no token count, and no cost signal for the investigation itself.

That's the same "flying blind" story SigNoz tells about LLM apps, applied one layer up.

## What we built

1. **Foundry-deployed SigNoz** with the MCP server enabled (`casting.yaml` + lock in the repo — a field requirement).
2. A **fault-injectable demo chain** on Kubernetes (`checkout-api` → `payment-svc` → `inventory-svc`) exporting OTLP to Foundry.
3. **Incident Sentinel** — FastAPI webhook + agent loop that calls SigNoz MCP tools (`signoz_search_traces`, `signoz_get_trace_details`, `signoz_search_logs`, …).
4. A Slack report with evidence deep links back into SigNoz.
5. Self-telemetry: `sentinel.investigate` root spans, GenAI chat spans (`gen_ai.usage.*`), tool spans, and metrics (`sentinel_tokens_total`, `sentinel_cost_usd_total`, …).

kagent packaging is documented as a **stretch** deployment mode. The core loop is custom so we own GenAI attributes and cost metrics end-to-end.

## What broke (the useful part)

- **foundryctl on EL8:** binary needs newer glibc. We ran it in a Debian container with the host Docker socket + CLI mounted.
- **ClickHouse Keeper `25.12.5` SIGSEGV (exit 139)** on our Docker host. Pinning `clickhouse-keeper:24.8.14` made the stack healthy.
- **Register before trusting ingestion.** UI/`/api/v1/register` must complete before MCP/tools and OTLP feel "real."
- **Mock LLM mode** for demos without API keys: the agent still exercises MCP + OTel cost counters so the self-observability story works offline.

## Favorite design decision

The meta-alert: a cost budget on `sentinel_cost_usd_total`.

If the copilot spends too much investigating, *it* pages you.

The watcher is watched — and this is not hypothetical. During testing, three investigations with `llama-3.1-70b-instruct` (~$0.005 each at market pricing) blew through our demo budget of $0.01/hour. SigNoz fired `sentinel-cost-budget`, routed it to the copilot's own webhook, and **the copilot investigated its own cost overrun and posted the report to Slack**. Full circle.

## Measuring the agent (instead of trusting it)

The most common gap in AI-for-SRE demos: nobody asks "how often is the agent *right*?"

We built a small eval harness (`evals/`) that injects **real faults** into the demo chain — error spikes, latency-only degradation, a failing downstream dependency — waits for telemetry, runs a full investigation, and scores the verdict **strictly**: the conclusion's `service` field must name the true culprit and the root cause must describe the right failure mode. Echoing the alert name doesn't count.

The first honest run taught us something real: the agent once blamed `incident-sentinel` — *itself* — for a latency incident, because its own investigation spans live in the same SigNoz it queries. Self-observability polluting self-investigation is exactly the kind of failure mode you only find by measuring. (The fix: the agent's prompt now excludes its own service and anchors on the alerted service's dependency chain.)

Results live in `evals/RESULTS.md`, regenerated by `python3 evals/run_evals.py`.

## Beyond diagnosis: postmortems (not auto-remediation)

Every investigation produces an **auto-generated markdown postmortem** — timeline, impact, evidence with SigNoz links, action items, investigation cost — posted to Slack and served at `GET /postmortems/{ruleId}`.

We intentionally do **not** auto-remediate. The copilot's job is fast, evidence-backed diagnosis; humans keep the execute button. That boundary is a feature for enterprise trust.

## Agent Quality dashboard

Besides Copilot Operations (tool/LLM spans), SigNoz hosts an **Agent Quality** dashboard: investigation volume, cost, and `sentinel_eval_pass_ratio` / pass-fail counters emitted by the eval harness. Accuracy is a first-class observability signal — not a blog claim.

## Enterprise-readiness details

A hackathon agent that would survive contact with production needs more than a happy path:

- **Graceful degradation:** if the LLM times out or never produces a valid conclusion, the report is synthesized *only* from the raw MCP evidence (extracted services and error lines), flagged `degraded: true`, and Slack shows a visible degraded-mode tag. No hallucinated root causes.
- **Async webhook handling:** the webhook acks immediately and investigates in the background, so slow big-model completions never time out alert delivery.
- **Guardrails:** dedupe window per alert rule, concurrency cap, bounded investigation steps, LLM retry-on-timeout.
- **Least privilege:** SigNoz access via a scoped Service Account API key in a Kubernetes Secret — no user JWTs.
- **Cost accountability:** every investigation records tokens, USD cost, and duration as metrics — the same budget alert above closes the loop.

## Demo script (2–3 minutes)

1. `./demo/break.sh errors`
2. Wait for `checkout-error-spike` (or POST `/investigate` manually)
3. Show Slack root-cause report with SigNoz links (~13 seconds end-to-end with the 70B model)
4. Open SigNoz → service `incident-sentinel` → investigation trace with token attributes
5. Open **Copilot Operations** dashboard panels
6. Show the `sentinel-cost-budget` meta-alert — the copilot policing its own spend

## Takeaways

Observability for AI agents isn't only "trace the LLM app."

Sometimes the agent *is* your SRE workflow.

Instrument both sides — the incident and the investigation — on one OpenTelemetry-native backend.
